# Hog: primary-source research

Research notes for a minimal, high-performance TypeScript/Bun agent framework. Links below are to the owner of the API, runtime, specification, or original research.

## Design implications at a glance

- Keep the core as an explicit, bounded **model → tool calls → validated observations → model** loop. The provider returns a proposed call; the host owns tool execution, ordering, errors, cancellation, and the stopping policy.
- Make streaming, tool calling, and strict structured output separate capabilities on a model/request profile. In Groq today, strict structured output cannot be combined with either streaming or tools.
- Treat an `AbortSignal` and an `AsyncIterable` event stream as the smallest useful run-control surface. Do not invent a second cancellation protocol or eagerly buffer streamed deltas.
- Make tracing and durable storage optional adapters. If durability is enabled, checkpoint after named side effects and persist small, serializable facts—not a growing transcript or opaque in-memory state.

## Groq chat-completions provider

- Groq exposes the OpenAI-compatible `POST /openai/v1/chat/completions` endpoint; its compatibility guide documents both the OpenAI-SDK base URL and incompatibilities. Use the normal chat-completions abstraction, but retain a provider capability table rather than assuming every OpenAI option works. [Groq OpenAI compatibility](https://console.groq.com/docs/openai) · [chat API reference](https://console.groq.com/docs/api-reference)
- `stream: true` produces server-sent events / completion deltas. Surface deltas incrementally as framework events, with no implicit aggregation requirement; aggregation can be a consumer convenience. [Groq chat API reference](https://console.groq.com/docs/api-reference) · [streaming guide](https://console.groq.com/docs/text-chat#streaming-a-chat-completion)
- Local tools are host-orchestrated: an assistant response with `finish_reason: "tool_calls"` carries `tool_calls`; each call has an id, function name, and JSON-string arguments. The host executes it, appends a `role: "tool"` result associated by `tool_call_id`, then asks the model again. Continue only until no calls remain or a framework limit/cancellation policy wins. Groq also documents `tool_choice` and `parallel_tool_calls`; execution concurrency must therefore be an explicit host policy, not accidental `Promise.all`. [Groq local tool-calling guide](https://console.groq.com/docs/tool-use/local-tool-calling) · [API reference](https://console.groq.com/docs/api-reference)
- `response_format: { type: "json_schema", json_schema: ... }` requests Structured Outputs on supported models; strict mode uses constrained decoding, requires every field to be required and objects to disallow additional properties. However, **streaming and tool use are currently unsupported with Structured Outputs**. For the other modes, retain runtime validation even when JSON mode makes syntactic JSON likely. [Groq Structured Outputs](https://console.groq.com/docs/structured-outputs)
- Capture provider usage from the terminal completion (`input`/`output`/`total` tokens and applicable detailed usage) and timing metadata, instead of locally estimating it. Cached-input usage is separately reported, and Groq defines total tokens as prompt plus completion tokens. [Groq API reference](https://console.groq.com/docs/api-reference) · [Groq prompt caching](https://console.groq.com/docs/prompt-caching)

## Zod 4 boundaries and JSON Schema

- Use a Zod schema as the single host-side contract for tool arguments, tool results if exposed to consumers, and final structured data. `safeParse` returns a discriminated success/error result, making malformed model JSON a normal, recoverable boundary outcome rather than an unchecked cast. [Zod basics](https://zod.dev/basics)
- Zod 4 natively converts schemas via `z.toJSONSchema(schema)` (Draft 2020-12 by default), eliminating a conversion dependency for a Groq schema request. Object schemas emit `additionalProperties: false` by default, which aligns with Groq strict-output requirements. [Zod JSON Schema](https://zod.dev/json-schema) · [Zod 4](https://zod.dev/v4)
- Conversion is deliberately not universal: e.g. `date`, `transform`, `bigint`, and `map` do not have JSON-Schema representations and throw by default. Restrict provider-facing schemas to representable data or explicitly handle the conversion policy; do not silently advertise a schema that differs from runtime validation. [Zod JSON Schema](https://zod.dev/json-schema)

## Streaming, pause/resume, cancellation, and backpressure

- ECMAScript defines an async iterable as an object whose `Symbol.asyncIterator` returns an async iterator. Its optional `return()` tells the iterator the consumer will make no more `next()` calls. This supports early consumer exit/cleanup and makes `AsyncIterable<RunEvent>` a portable streaming seam. [ECMAScript async-iterator interface](https://tc39.es/ecma262/2025/multipage/control-abstraction-objects.html#sec-asynciterator-interface)
- Bun implements Web `AbortController`/`AbortSignal`; its `fetch` accepts a signal and can be cancelled through the controller. It also accepts async generators/async iterables as response streams. Pass a single run signal through model requests, tools, and subprocesses, and make a cancelled run terminal rather than relying on consumer disconnect alone. [Bun globals](https://bun.sh/docs/runtime/globals) · [Bun fetch cancellation](https://bun.sh/docs/runtime/networking/fetch) · [Bun async-generator streams](https://bun.sh/docs/runtime/streams)
- Web Streams has an actual flow-control signal: `desiredSize` is derived from queue capacity, and producers can slow when it is non-positive; `WritableStreamDefaultWriter.ready` resolves when backpressure subsides. `pipeTo` propagates this through a chain. Use it at HTTP/byte-stream boundaries. An agent-event `AsyncIterable` is pull-based only when the producer waits for `next()`; otherwise it needs a bounded queue and an explicit overflow policy. [WHATWG Streams Standard: backpressure](https://streams.spec.whatwg.org/#backpressure)
- “Pause” has two different meanings. Transport flow control can stop pulling/producing events; durable pause means persist a checkpoint and later recreate/replay the run. Keep these concepts separate in the public API.

## OpenTelemetry tracing and GenAI conventions

- OpenTelemetry’s GenAI semantic conventions now live in their own official repository, covering spans, metrics, events, client calls, MCP, and provider-specific conventions. Adopt ordinary parent/child spans around a run, model call, and tool execution, then export via standard OpenTelemetry plumbing. [OpenTelemetry GenAI semantic conventions repository](https://github.com/open-telemetry/semantic-conventions-genai) · [migration notice](https://opentelemetry.io/docs/specs/semconv/gen-ai/)
- The GenAI registry provides operation names including `chat`, `invoke_agent`, and `execute_tool`, plus attributes for provider/model, output type, token usage, and errors. Prefer these bounded fields over raw prompts/completions as always-on span attributes; make content capture opt-in and apply redaction. [GenAI attribute registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)
- Stability is a real compatibility constraint: conventions have maturity levels from `development` through `stable`; stable instrumentations must not emit unstable conventions by default and may make them opt-in. GenAI conventions recently moved repositories and prior `gen_ai.*` definitions were deprecated, so encapsulate semantic-convention names and schema URLs in one adapter/versioned mapping rather than leak them through Hog’s core API. [semantic-convention stability](https://opentelemetry.io/docs/specs/semconv/general/semantic-convention-groups/) · [migration release notes](https://github.com/open-telemetry/semantic-conventions/releases/tag/v1.42.0)

## Agent loop, tool use, and durability

- ReAct is the original framing for interleaving reasoning traces and external actions: reasoning updates the plan and handles exceptions; actions obtain observations from external environments. It supports the minimal loop above, but does not require exposing private reasoning in framework events or traces. [Yao et al., *ReAct* (original paper)](https://arxiv.org/abs/2210.03629)
- Toolformer independently motivates the mechanics a framework must make reliable: decide whether/when to call an API, construct arguments, and incorporate its result into later prediction. Framework-level schemas, validation, result correlation, limits, and auditability are the non-model half of that contract. [Schick et al., *Toolformer* (original paper)](https://arxiv.org/abs/2302.04761)
- A durable execution reference model: an operation’s named result is checkpointed; on restart, deterministic code replays and receives stored results instead of rerunning completed operations. The AWS Durable Execution SDK explicitly warns that non-deterministic work and side effects must be inside durable steps, and that static step names form replay identity. Those are sound constraints if Hog adds an optional durable adapter. [AWS Lambda durable execution concepts](https://docs.aws.amazon.com/lambda/latest/dg/durable-basic-concepts.html) · [AWS durable step design](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/step-design/)
- Checkpoint only the minimal resume state: checkpoint size increases storage and replay deserialization work; durable state must be serialized, while locals between steps do not survive. For an agent this suggests recording run id, model/request identity, normalized message/tool ledger, completed tool idempotency keys/results, step counter, and terminal status—while storing bulky artifacts by reference. [AWS durable state guidance](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/state/)
- Durable execution changes the tool contract: replays can repeat orchestration code, so external-effecting tools need stable call identities and idempotency handling. A high-performance default can remain in-memory/ephemeral; durability should be opt-in because persistence, serialization, and history retention are costs and operational commitments.

## Proposed narrow foundation

1. **Typed boundaries:** Zod input/output schemas; JSON-Schema conversion only at the provider boundary; validate every model-supplied tool argument and final payload.
2. **One bounded loop:** max turns, tool timeout/cancellation, tool concurrency policy, explicit tool-error observation, and terminal usage accounting.
3. **One event channel:** `AsyncIterable` lifecycle/delta/tool events plus a shared `AbortSignal`; consumers choose rendering, storage, and network adaptation.
4. **Optional adapters:** provider (Groq), tracer (OpenTelemetry), and checkpoint store. Core run state stays plain, serializable data so an adapter can persist it without coupling the fast path to a database.
