# Hog Python: primary-source research

Research for a minimal Python translation of Hog Build Quest, verified 2026-09-15. All links are to official documentation, source repositories, specifications, or original papers. “Recommendation” is an engineering inference; the surrounding cited statements are factual API/runtime claims.

## Practical shape

**Recommendation:** make the core provider-neutral but initially ship only a Groq adapter. Keep it to four seams: a message/tool ledger, an async provider protocol, a bounded local-tool loop, and an `AsyncIterator` event surface. Do not let Groq SDK response types leak beyond its adapter; use plain, immutable-ish application records at the core boundary.

Groq’s own local-tool documentation describes the necessary host loop: send JSON-Schema tool definitions; receive `tool_calls`; parse and run the local calls; append result messages correlated with `tool_call_id`; call the model again; repeat until no calls remain or a host-set maximum is reached. The host—not the model or SDK—owns execution, security, validation, cancellation, and the iteration bound. [Groq local tool calling](https://console.groq.com/docs/tool-use/local-tool-calling) · [original ReAct paper](https://arxiv.org/abs/2210.03629) · [original Toolformer paper](https://arxiv.org/abs/2302.04761)

## `asyncio`: events, cancellation, timeout, streams

- An `asyncio.Event` is a non-thread-safe broadcast flag: `wait()` blocks until `set()`, and `set()` awakens every waiting task. It is suitable for a cooperative run-cancel/pause signal within one event loop, but not as a cross-thread primitive or durable state. [Python `asyncio` synchronization primitives](https://docs.python.org/3/library/asyncio-sync.html)
- A bounded `asyncio.Queue(maxsize=N)` gives real in-process backpressure: awaited `put()` blocks while full until a consumer removes an item. The default `maxsize=0` is unbounded, so it is the wrong default for untrusted/slow event consumers. Queue operations are not thread-safe; Python 3.13 also provides queue shutdown semantics. **Recommendation:** use a small bounded queue only when decoupling a producer from a consumer is necessary; otherwise let a single async generator naturally pace event production. [Python `asyncio.Queue`](https://docs.python.org/3/library/asyncio-queue.html)
- An async generator’s `__anext__()` is normally driven by `async for`. If consumption stops early (break, cancellation, or exception), the language reference says the caller must call `aclose()` to run async cleanup reliably; `aclose()` injects `GeneratorExit` at the paused yield. **Recommendation:** expose run events as an async generator and ensure any adapter that abandons it calls `aclose()` in `finally`. [Python async-generator specification](https://docs.python.org/3/reference/expressions.html#asynchronous-generator-iterator-methods)
- Cancelling a task raises `asyncio.CancelledError` at its next suspension point. Use `try/finally` for tool/client cleanup and normally re-raise the exception: `TaskGroup` and `asyncio.timeout()` use cancellation internally and may misbehave if it is swallowed. A `TaskGroup` cancels remaining children after the first non-cancellation failure and raises an exception group after all finish. [Python task cancellation and `TaskGroup`](https://docs.python.org/3/library/asyncio-task.html)
- `asyncio.timeout()` (Python 3.11+) is a nestable async context manager that cancels the current task at its deadline and converts that cancellation into catchable `TimeoutError` outside its block. `wait_for()` cancels the awaited object on timeout (unless shielded), and may exceed its nominal duration while waiting for cancellation to complete. **Recommendation:** set a run-level deadline with `asyncio.timeout_at()` and smaller, explicit provider/tool deadlines; do not layer unrelated retries inside a cancelled tool operation. [Python timeout APIs](https://docs.python.org/3/library/asyncio-task.html#timeouts)
- Keep strong references to background tasks: the event loop holds weak references and an otherwise-unreferenced task can be garbage-collected before completion. [Python task documentation](https://docs.python.org/3/library/asyncio-task.html)

## Compact state and honest memory measurements

- `@dataclass(slots=True)` causes a dataclass to generate `__slots__`. Slots omit the per-instance `__dict__`/`__weakref__` by default; Python documents potentially significant space savings and faster attribute lookup. `weakref_slot=True` only works with `slots=True` and adds the needed weak-reference slot. **Recommendation:** use slotted standard-library dataclasses for frequent, closed-shape event/message records; reserve Pydantic models for untrusted provider/tool boundaries. [Python dataclasses](https://docs.python.org/3/library/dataclasses.html) · [Python data model: `__slots__`](https://docs.python.org/3/reference/datamodel.html#slots)
- `tracemalloc` traces Python allocations and gives allocation traceback/statistics plus current/peak *traced* memory. It should start early for leak comparisons; retaining more traceback frames raises its own CPU/memory overhead. `resource.getrusage(RUSAGE_SELF).ru_maxrss` is the process maximum resident set size on platforms that provide `resource`. **Recommendation:** record both in a controlled benchmark: `tracemalloc` answers “which Python allocation grew?”, while RSS captures process footprint (including allocator/runtime/native allocations) but `ru_maxrss` is a high-water mark, not current RSS. [Python `tracemalloc`](https://docs.python.org/3/library/tracemalloc.html) · [Python `resource`](https://docs.python.org/3/library/resource.html)
- `sys.getsizeof()` is not a process or graph measurement: it only counts memory directly attributed to an object, not objects it refers to. Do not use it to compare whole conversations or framework memory. [Python `sys.getsizeof`](https://docs.python.org/3/library/sys.html#sys.getsizeof)

## Pydantic v2 at the boundary

- Pydantic is coercive by default. Strict validation can be selected per call, per field, or through `ConfigDict(strict=True)`; strict JSON validation is deliberately a little looser for JSON-native representations (for example, date/time strings). **Recommendation:** validate model-supplied tool arguments and final structured responses with `strict=True`, then make the few permitted conversions explicit in schemas rather than rely on lax coercion. [Pydantic strict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/)
- `BaseModel.model_validate_json()` accepts JSON `str`/`bytes` and is generally faster than `model_validate(json.loads(...))` because it avoids materializing an intermediate Python dict; it also accepts validation controls such as strictness. `TypeAdapter.validate_json()` provides the corresponding type-first path. [Pydantic model validation](https://docs.pydantic.dev/latest/concepts/models/#validating-data) · [Pydantic performance guidance](https://docs.pydantic.dev/latest/concepts/performance/)
- Construct a `TypeAdapter` once and reuse it: each construction builds a validator and serializer. **Recommendation:** compile one adapter per stable tool schema/final-output type at registration time, not inside the hot tool loop. [Pydantic TypeAdapter performance guidance](https://docs.pydantic.dev/latest/concepts/performance/#typeadapter-instantiated-once)
- `BaseModel.model_json_schema()` and `TypeAdapter.json_schema()` produce JSONable schemas (Pydantic documents Draft 2020-12/OpenAPI 3.1 support; default mode is validation). These provide the Groq tool/structured-output schema boundary. **Recommendation:** test exported schemas against Groq’s stricter subset rather than assume every valid Pydantic schema is accepted in strict mode. [Pydantic JSON Schema](https://docs.pydantic.dev/latest/concepts/json_schema/)

## Groq Python client and streaming

- `groq-python` is Groq’s official Python library (Python 3.10+). `AsyncGroq` has the same API shape as the synchronous client and is powered by `httpx`; optionally `DefaultAioHttpClient` uses `aiohttp`, which the SDK presents as a concurrency-performance option. **Recommendation:** create one application-lifetime `AsyncGroq` per credential/base URL to preserve its underlying HTTP client resources; use `async with AsyncGroq(...)` at application lifespan boundaries or explicitly close it. [official `groq-python` README](https://github.com/groq/groq-python#async-usage) · [client resource management](https://github.com/groq/groq-python#managing-http-resources)
- For chat SSE, await `client.chat.completions.create(..., stream=True)`, then consume with `async for`. The separate `with_streaming_response` API is raw HTTP-body streaming; it requires a context manager to reliably close the response. **Recommendation:** use chat SSE for framework deltas and only expose raw streaming as a lower-level adapter escape hatch. [Groq Python streaming](https://github.com/groq/groq-python#streaming-responses) · [raw streaming response lifecycle](https://github.com/groq/groq-python#with_streaming_response)
- The SDK automatically retries connection failures and HTTP 408, 409, 429, and 5xx twice by default with short exponential backoff; retry count is configurable globally or per request. Default request timeout is one minute, and timed-out requests are also retried by default. **Recommendation:** make the framework retry budget explicit and conservative for an agent loop—especially for side-effecting tools—and coordinate it with an outer `asyncio` deadline so latency is bounded. [Groq Python retries and timeouts](https://github.com/groq/groq-python#retries)
- A streamed tool call is incremental data: Groq’s streaming-tool example collects `delta.tool_calls` chunks and waits for `finish_reason == "tool_calls"` before executing. **Recommendation:** accumulate fragments by call/index into a complete assistant turn, validate parsed arguments exactly once, and never execute a partial argument string. [Groq streaming local tools](https://console.groq.com/docs/tool-use/local-tool-calling#streaming-tool-use)
- Completed chat responses carry `usage` token fields; capture provider-reported usage and timings at the end of each completed model call, not by re-tokenizing locally. [Groq chat API reference](https://console.groq.com/docs/api-reference) · [Groq prompt-cache usage](https://console.groq.com/docs/prompt-caching)

## Groq structured output: hard capability fork

As of 2026-09-15, `response_format.type = "json_schema"` offers strict (`strict: true`) constrained decoding for `openai/gpt-oss-20b`, `openai/gpt-oss-120b`, and `qwen/qwen3.8-27b`. Strict schemas require all fields to be required and every object to set `additionalProperties: false`; best-effort schema output has broader but imperfect support. The documented hard limitation is that **streaming and tool use are not currently supported with Structured Outputs**. Other models can use JSON Object Mode, which does not guarantee schema conformance. [Groq Structured Outputs](https://console.groq.com/docs/structured-outputs)

**Recommendation:** represent `text/stream`, `tool-loop`, and `strict-final-object` as distinct request/run modes. For a tool-using run that needs a typed final answer, first complete the tool loop, then make a final non-streaming strict-structured request (or validate a JSON-mode final response with Pydantic). Do not attempt a single request that requests all three capabilities.

## Optional OpenTelemetry across `asyncio`

- Python `ContextVar`s are natively supported in `asyncio`; a created `Task` copies the current context unless a different context is supplied. This is the basis on which an active OpenTelemetry span can flow through normal awaits and child task creation. [Python `contextvars` asyncio support](https://docs.python.org/3/library/contextvars.html#asyncio-support) · [Python `Task` context](https://docs.python.org/3/library/asyncio-task.html)
- OpenTelemetry Python traces are stable, while its documentation warns that use of experimental semantic conventions can still change. The official API guidance says instrumenting a library should depend on the API, allowing the application to choose/configure the SDK; it also recommends active/current spans for correlating nested instrumentation and log events. [OpenTelemetry Python status](https://opentelemetry.io/docs/languages/python/) · [Python instrumentation guidance](https://opentelemetry.io/docs/languages/python/instrumentation/) · [OpenTelemetry library guidance](https://opentelemetry.io/docs/concepts/instrumentation/libraries/)

**Recommendation:** make tracing a no-op optional adapter. Capture the current context at public run/tool-task boundaries, create a parent run span with model/tool child spans, and pass explicit context when dispatching work outside normal asyncio task flow (threads, callbacks, external queues). Keep GenAI semantic-convention keys confined to that adapter because their conventions are still evolving.
